# 取舍与踩坑记录

这份笔记不是验收报告，主要记录我在做这个框架时怎么拆问题、哪些选择其实有替代方案，以及几次真实的调试过程。验收表只写结果，这里写“为什么”。

## 1. 为什么按这个顺序做

我没有一上来就把 FreeRTOS、CAN、IMU、舵机全部接在一起，而是先把“能看见、能测量”的链路逐个打通：

1. 时钟、串口、PWM 这种最基础的输出；
2. 再让 UART 能稳定收发；
3. 再把指令解析、CRC 和舵机动作接起来；
4. 最后才加 FreeRTOS、队列、健康监测和 IWDG。

这样做的原因很实际：如果一开始就上 RTOS，出问题时很难判断是时钟、串口、任务优先级还是看门狗。每加一层只引入一个新变量，出错时容易回退。

## 2. 几个关键选择

### 5 秒回中

这是应用层策略，不是安全急停。舵机失联后回到中位，比保持最后位置更容易观察，也不会让机构一直顶在一边。

我考虑过 3 秒和 10 秒：

- 3 秒太急，操作员短暂停顿就会回中；
- 10 秒又太慢，演示时看不出“失联”；
- 5 秒是一个便于演示和观察的折中，不是行业标准。

所以文档里写的是“当前策略”，不是“正确参数”。

### 健康窗口 500 ms、IWDG 约 3 秒

IWDG 用 `Prescaler=64`、`Reload=1499`，按 LSI 32 kHz 估算约 3 秒。健康任务每 500 ms 检查一次，理论上 3 秒内有多次机会发现缺席。

这里我还没有做最坏调度延迟分析。500 ms 是让健康任务的开销足够小，同时保证在 3 秒超时前能发现一次缺席；如果以后任务更多，需要重新算。

### 队列等待 100 ms

输出任务不是忙等，而是用 100 ms 超时定期醒来：

- 有指令就立即处理；
- 没指令时检查 5 秒保持时间；
- 100 ms 让回中最多晚一个检查周期，同时不会每秒醒来几百次。

我没有做 CPU 占用测量，这个值目前是“够用且不笨”的选择。

### 阻塞 UART 作为最终方案

代码里保留过 IT/DMA 的 UART 实验，但最终舵机链路用的是阻塞单字节接收：

- 命令很短，115200 下单字节间隔足够；
- 10 ms 超时让 RX 任务能定期让出 CPU；
- 逻辑简单，调试时容易判断是收到字节还是超时。

IT/DMA 不是没做，而是这一版不需要。这个取舍应该由“未来是否有高吞吐串口需求”决定，不是默认越复杂越好。

### 队列深度 4 和 1024 B 栈

队列深度 4 是为了覆盖“一条指令正在执行、后面又来一两条”的短突发；没有做压力测试，所以不能宣称能抗任意洪峰。

1024 B 栈来自实测：L8-5 的 Debug 联调固件里，RX 任务最小剩余 764 B，输出任务最小剩余 824 B。它们看起来够用，但健康任务和 Release 的栈余量还没测，所以文档里特意标了阶段，不把旧数据当成当前结论。

### CRC-8 和帧格式

选 CRC-8/SMBUS 是因为帧很短、开销小，标准向量 `123456789 -> 0xF4` 也容易做主机测试。

CRC 只覆盖 `*` 前的 ASCII，例如 `S50*B1` 只算 `S50`。这样做的好处是解析器可以在校验前先确认位置字段，缺点是协议没有长度、版本和序列号。目前它是台架协议，不是安全关键协议；如果上真实机构，应该重新考虑 CRC-16 和帧头。

### F103 只做 UART/PWM

F103 这一轮只验证“同一套 BSP、CRC 解析器、SG90 驱动能不能跨芯片跑”，所以没有把 FreeRTOS、健康监测和 5 秒状态机搬过去。

这也意味着 F103 demo 里目前混了 port 和应用循环。我知道这个边界不完美：`F103Uart` 是 port 适配，`run_f103_servo_demo` 更像 example。当前优先保证可验证，后面如果要继续扩展，应该把它拆成 `port/stm32f1` 的 UART 类和单独的 example。

### 日志只做启动期

`bsp::ILog` 的首版实现成启动期、单调用者、阻塞输出，是因为 USART1 在调度开始后归 `servo_rx` 任务使用。启动阶段没有并发，直接发送最简单，也不会和任务抢串口。

运行期日志还没有做。要让日志和命令接收共存，至少需要队列、锁或者独立串口；这是下一轮的事，不应该在文档里假装已经解决。

## 3. 踩过的坑

### J-Link 接错目标

有一轮 J-Link 还接在 F103 上，我按 F407 去烧录，读到的却是 Cortex-M3，DBGMCU ID 是 `0x410`，不是 F407 的 `0x413`。后来先读目标 ID，确认板子再下载，才避免把固件烧到错误目标。

这个检查现在应该固定成流程，而不是靠记忆。

### 串口必须先打开再复位

启动日志只发一次。最开始我先复位、再打开 COM7，结果什么都收不到，误以为是 UART 发送坏了。后来改成“先打开串口，写入一个 OPEN 标记，再复位”，才稳定抓到：

```text
[INFO] USART1 ready
[WARN] IMU identity unsupported
```

### PA9/TTL RXD 这根线

调试 F103 时，PC 发给板子的指令能收到，但板子发回 PC 的启动消息收不到。原因排查到最后是发送方向没接好：TTL 的 TXD 接到了 PA10，但 TTL 的 RXD 没有可靠接到 PA9。

这件事让我后来在文档里把“TTL TXD -> PA10、TTL RXD -> PA9、GND 共地”写成了固定检查项。

### IWDG 注入

测试健康监测时，我人为让输出任务不报到，观察 `servo_health_missing` 是否变成 `0x02`，然后等硬件看门狗复位。复位前后读 `boot_reset_csr`：

- 复位前：`0x14000000`，IWDGRSTF 为 0；
- 复位后：`0x24000000`，IWDGRSTF 为 `0x20000000`。

这比只看“程序重启了”更有说服力，因为能区分普通复位和 IWDG 复位。

## 4. 还没想清楚的地方

- 健康任务和 Release 的栈余量还没测，不能拿 L8-5 的数字直接外推。
- 5 秒、500 ms、100 ms 都是当前演示参数，没有做用户手感测试或最坏延迟分析。
- 队列满时 RX 任务直接进 `Error_Handler`，这是 fail-stop，不是背压设计；真实系统可能需要丢帧或重试策略。
- F103 的 demo/port 边界需要再拆一次。
- 运行期日志、HC-05 断链、外部 CAN 和真实 MPU6050 都还没有验证。

这些不是“待办清单式”的假谦虚，而是我目前确实没有数据支撑的部分。

## 5. 如果只让我重做一件事

我会把“决策记录”放在写代码之前，而不是验收之后补。比如先写：

```text
问题：失联后舵机怎么处理？
选项：保持 / 回中 / 断电
选择：回中
理由：演示可见、机构不长期受力
风险：回中过程中可能经过障碍
```

这样后面代码和测试都能对着这个决定解释，而不是做完之后从结果倒推理由。
